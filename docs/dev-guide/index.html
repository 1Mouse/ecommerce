Express gives you freedom, which can feel like chaos. This project uses that freedom with a clear rule: keep HTTP, business logic, persistence, and wiring separated so the code can grow from auth into products, orders, payments, chat, jobs, and multi-tenancy.

Why Express Feels All Over The Place

Express is unopinionated

It does not force controllers, services, repositories, modules, decorators, or dependency injection. That is why two Express apps can look completely different.

Middleware is powerful

Almost everything is a function in a pipeline: security, CORS, JSON parsing, logging, auth checks, validation, routes, 404s, and errors.

Architecture is your job

The framework handles HTTP. We decide the application structure. Our goal is not to add complexity, but to put each concern in a predictable place.

The practical mindset

Enterprise style does not mean adding every pattern early. It means clear boundaries, boring conventions, testable business logic, and infrastructure that can be replaced without rewriting the app.

What each area means

Where to put new code
app.ts Express application setup: global middleware, public routes, module routes, 404 handler, error handler.
server.ts Runtime bootstrap: load env, connect Mongo, listen on port, graceful shutdown.
container.ts Composition root: creates services, repositories, and controllers in one place.
modules/ Feature areas. Auth is a feature. Products, orders, payments, chat, and tenants can become features too.
infrastructure/ External systems: MongoDB, future Postgres, Redis, object storage, email provider, payment SDK.
shared/ Cross-cutting backend utilities: errors, validation helpers, API response helpers, async route wrapper.

Express Pipeline In This Project

src/app.ts

Order matters
Security helmet() adds safer response headers.
Browser Access cors() controls which frontends can call the API.
Body Parser express.json() parses JSON request bodies. Multipart uploads will use route-level middleware later.
Logging pinoHttp() logs requests and responses.
Routes + Errors Routes first, then 404 handler, then global error handler.

Remember this rule

Express runs middleware top to bottom. Parsers and security go before routes. notFoundHandler and errorHandler go at the end.

Auth Architecture

Signup/login/refresh

Why several files exist

Route

auth.routes.ts maps URLs like /signup and /login to controller methods.

Controller

auth.controller.ts reads HTTP input and sends HTTP responses. It should stay thin.

Schema

auth.schemas.ts validates request bodies with Zod before the service trusts them.

Service

auth.service.ts owns the application workflow: create user, verify password, rotate refresh token.

Repositories

Repositories hide Mongoose so the service does not need to know database query details.

Token model

Current security choices
Piece Meaning
Access token Short-lived JWT used to call protected routes later.
Refresh token Longer-lived token used to get a new access token.
Refresh hash The database stores a SHA-256 hash, not the raw refresh token.
Rotation When refresh succeeds, the old refresh token is revoked and a new one is created.
Password hash Passwords are stored with bcryptjs, never as plain text.

Architecture Rules

Business Rules

Keep the important logic away from framework details.

Controllers do HTTP

They receive requests, call services, and return responses. They should not contain database queries or deep business rules.

Services orchestrate

They coordinate validation results, repositories, password hashing, token creation, and domain decisions.

Repositories persist

They translate between app objects and database models. Mongoose should stay near this boundary.

Do not over-engineer too early

We are using enterprise-shaped boundaries, not full enterprise ceremony. We will introduce stricter DDD, CQRS, events, queues, and adapters only when the project needs them.

Architecture Ahead

Protected routes

Add access-token middleware and a GET /api/v1/me route. This teaches auth guards and request context.

Products module

Add products with JSON first, then image upload with route-level multipart middleware such as Multer.

Orders module

Model order placement as a business workflow, not just CRUD. This is where domain rules become more interesting.

Payments

Add a payment adapter boundary so Stripe or another provider does not leak into the core order workflow.

Background jobs and cron

Add scheduled work for cleanup, token expiry, emails, reports, or abandoned carts.

WebSockets and streaming

Add chat and an AI chatbot to practice persistent connections and streaming responses.

Multi-tenancy and database adapters

Introduce tenant context and eventually a Postgres adapter where it teaches useful architecture instead of adding accidental complexity.
