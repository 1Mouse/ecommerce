Joins, Pipelines, and $unwind

This lesson compares the relational Postgres way of combining rows with the MongoDB document way of reshaping documents. The ecommerce goal is practical: know when to reference, when to embed, and how to query across collections without confusing MongoDB with SQL.

Postgres joins MongoDB aggregation $lookup $unwind Ecommerce persistence

Mental Model

Postgres: keep related facts in tables, combine rows at query time with joins.

MongoDB: keep data you read together in documents, use aggregation stages to filter, join, flatten, group, and reshape documents.

1. What A Join Does

A join combines records from two sources using a rule. In ecommerce, that rule might be: orders.user_id = users.id or orders.userId = users._id.

Inner Join

Only rows with a match on both sides survive.

Left Outer Join

Every left-side row survives. Missing right-side data becomes null.

Right Outer Join

The mirror of a left join. Every right-side row survives.

Full Outer Join

All rows from both sides survive. Non-matches get null on the missing side.

Cross Join

Every row from one side pairs with every row from the other. Use carefully.

Self Join

A table joins to itself, usually with aliases. Useful for comparing records in the same table.

Postgres documentation introduces joins as queries that combine rows from tables, with a join condition saying which rows should be paired.

2. The MongoDB Aggregation Pipeline

An aggregation pipeline is an ordered list of stages. Each stage receives documents, transforms or filters them, then passes the result to the next stage.

$matchfilter documents
$lookupattach matching documents from another collection
$unwindturn array elements into separate documents
$groupaggregate by a key
$projectshape the output

The key difference from a normal SQL join is shape. SQL usually returns a flat table-shaped result. MongoDB returns documents, so a stage can add nested objects or arrays.

WHERE$matchKeep only matching documents.
JOIN$lookupAdd related documents from another collection.
GROUP BY$groupCombine documents by a key and calculate totals, counts, averages, etc.
ORDER BY$sortSort the current documents.

3. $lookup Is MongoDB's Join Stage

$lookup performs a left outer join to another collection in the same database. It adds a new array field containing matched documents.

{
  $lookup: {
    from: "users",
    localField: "userId",
    foreignField: "_id",
    as: "user"
  }
}

If an order matches one user, the result still looks like user: [ { ... } ]. If it matches no user, it looks like user: []. This is why $lookup often appears right before $unwind.

Important design point: MongoDB docs warn that excessive $lookup use can hurt performance. If data is usually read together, consider embedding it instead of joining it repeatedly.

4. $unwind Flattens Arrays

$unwind deconstructs an array field. One input document can become many output documents, one per array element.

Before

{
  _id: "order_1",
  items: ["keyboard", "mouse", "monitor"]
}

After $unwind: "$items"

{ _id: "order_1", items: "keyboard" }
{ _id: "order_1", items: "mouse" }
{ _id: "order_1", items: "monitor" }

By default, if the field is missing, null, or an empty array, MongoDB drops that document from the output. Use preserveNullAndEmptyArrays: true when you want to keep it.

{
  $unwind: {
    path: "$items",
    preserveNullAndEmptyArrays: true,
    includeArrayIndex: "itemIndex"
  }
}

5. Ecommerce Rule Of Thumb

QuestionPostgres instinctMongoDB instinct
Show an order with its line itemsJoin orders to order_items.Embed line items in the order document because they are read together.
Show an order with the user's emailJoin orders to users.Use $lookup if you need current user data, or store a snapshot if historical accuracy matters.
Report revenue by product categoryJoin, group, aggregate.$unwind order items, optionally $lookup products, then $group.

For orders, embedding purchased item name, SKU, unit price, and quantity is often correct because an order is a historical record. You usually do not want old order totals to change just because the product's current price changed.
